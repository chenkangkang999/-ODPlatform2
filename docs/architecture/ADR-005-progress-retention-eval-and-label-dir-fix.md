# ADR-005：进度反馈与 runs/ 保留策略；评估子系统的两套 IoU 口径；标签目录推导的缺陷修正

| 项目 | 内容 |
|---|---|
| 状态 | ✅ Accepted |
| 决策日期 | 2026-10-27 |

本篇一次记录三项工程决策 —— 它们的共同点是：**都源于"静默"造成的实际损失**
（静默地跑很久、静默地堆满磁盘、静默地把两套指标混着说、静默地数出 0 个真值框）。

---

## 决策一：长循环用"按比例打点的日志"做进度反馈，并给 `runs/` 一个可解释的保留策略

### 背景

**问题 A：长循环静默。** 数据流水线的扫描/物化、质检的逐样本核验、评估的数据集视图搭建与
置信度扫描，在大数据集上会**静默跑很久**，用户不知道是卡死了还是在干活。

**问题 B：`runs/` 没有保留策略。** 每次跑流水线都会在 `runs/` 下留一个现场目录
（推理输出、质检报告、划分 manifest、训练现场……），长期累积能吃掉几十 GB。
此前**没有任何保留策略** —— 只有 `odp-reset` 那种"整目录白名单清空"的粗暴手段，
没人敢在有真实产物时用它。

### 备选方案

- 进度反馈：① 引入 `tqdm`；② 自己写"按比例打点的日志"（**采纳**）；③ 什么都不做。
- 保留策略：① 不做，靠人手动删；② 按"总数上限"删最旧；③ 按"每个子目录保最新 N 个 **且**
  N 天内不动"的双条件策略（**采纳**）。

### 决定

**1. 进度反馈用日志打点，不用 `tqdm`。**

本仓库的可见性载体是**日志** —— `apps/platform/logging/` 与 `runs/` 下的文件，外加控制台。
`tqdm` 往 stderr 刷 `\r` 覆盖行：**落不进日志文件**，在 CI 日志里也只是一串转义字符，
事后无法回答"当时跑到哪儿卡住了"。所以 `common/progress.py` 做的是**按比例打点**：
每过一个档位记一行 `INFO`，带已完成/总数/百分比/速率/预计剩余。
因为"一行一条 INFO 日志"而不是"回车覆盖行"，在**非 TTY**（重定向到文件/管道）下
天然不会刷屏乱码 —— 落地的就是若干条完整的普通文本行。

打点规则（两条都满足才记）：

| 规则 | 常量 | 默认值 |
|---|---|---|
| 跨过预设的比例档位 | `DEFAULT_STEPS` | 10（每 10%） |
| 距上次打点至少这么多秒 | `MIN_INTERVAL_SEC` | `2.0` |
| 总量小于此值则关掉中间打点（一屏就完事了） | `MIN_TOTAL_FOR_INTERMEDIATE` | 50 |
| 总量未知（如"数一数有多少张图"）时按固定项数打点 | `UNKNOWN_TOTAL_STEP` | 1000 |

`finish()` 的收尾行**总是**记录（总数 / 总耗时 / 平均速率）。
`clock` 可注入，便于离线单测。

实际接入点（`ProgressReporter(...)` 的调用处）：

| 位置 | 名称 |
|---|---|
| `data_pipeline/convert/converters/pascal_voc.py` | VOC → YOLO 转换 |
| `data_pipeline/convert/converters/coco.py` | COCO → YOLO 转换 |
| `data_pipeline/orchestrator.py` | 清点图像 / 扫描图像目录 / 读取标签 |
| `data_pipeline/split/materializer.py` | 物化 processed |
| `data_validation/checks/manifest_lineage.py` | D4 manifest_lineage |
| `evaluation/dataset.py` | 搭建数据集视图 |
| `evaluation/service.py` | 置信度扫描 |
| `evaluation/iou.py` | IoU 匹配分析 |

**2. `runs/` 的保留策略：双条件，宁可留着。**

`common/retention.py` 的策略是：在每个受管子目录里保留

- **最新的 `keep_latest_per_group` 个**（默认 5），以及
- **修改时间在 `max_age_days` 之内的**（默认 30）；

其余才列入清理计划。**两个条件都满足才删** —— 于是"跑得多"不会把最近的产物删掉，
"跑得久"也不会把最新的删掉。

**`runs/lineage/` 被硬性排除**（`PROTECTED_SUBDIRS = ("lineage",)`）：那里存的是
D3/D4/D6 盖的**章** —— 数据出身链的凭据，`odp-train` 的身份核验靠它三方对账。
删了它，身份核验就再也对不上账，而且**无法重建**（重跑 D3 会换 manifest 指纹）。
它不靠"默认参数恰好没选到"，而是写死在策略里。

安全设计两条：

- **围栏校验**：`apply_cleanup()` 对每个候选先做 `_assert_within(runs_dir, path)`，
  拒绝操作沙盒根目录本身、拒绝沙盒外路径、拒绝符号链接（不做递归删除）；
  不合规的**跳过并告警**，不抛异常打断整场清理。
- **默认预演**：`odp-clean` 不加 `--yes` 只打印"打算删哪些、能释放多少"。
  这是本仓库对破坏性操作的统一态度（`odp-reset` 同理，它甚至要求交互式输入大写 `RESET`）。

配置来源：策略参数由**代码默认值**（`DEFAULT_KEEP_LATEST` / `DEFAULT_MAX_AGE_DAYS`）
与 `odp-clean` 的命令行参数提供，**不读取 runtime yaml** —— 本仓库当前没有任何 yaml
承载保留策略字段。

### 理由

1. 进度信息的消费场景是"**事后**回答当时跑到哪了"（排障 / CI 归档），
   而不是"盯着终端看"。日志是这个场景的正确载体。
2. 双条件策略可以被一句话解释清楚，用户能预测它会删什么 ——
   "猜你想删哪个"的清理工具没人敢用。
3. 把 `lineage` 的豁免做成代码常量而不是默认参数，是为了让"不能删"这件事
   在**参数被改错时依然成立**。

### 后果

- **正面**：长任务可观察；`runs/` 不再无限增长；`odp-clean --summary` 随时能看现状
  （真实输出示例见 [manual 2.9](../manual.md)）。
- **负面**：日志里的进度行比 `tqdm` 占的地方多（每 10% 一行，而不是一行反复刷新）；
  小数据集（< 50 项）只会有收尾一行 —— 这是有意的，避免刷屏。
- **中性**：保留策略参数不能通过 yaml 固化；要固定就用 shell 别名或 CI 脚本传参。

## 决策二：`odp-eval` 作为独立评估子系统，并把"官方 mAP 口径"与"匹配口径"并列而非混用

### 背景

`odp-train` 只在训练过程中顺带打印指标，没法"拿一个已经训好的权重单独跑评估、出结构化报告"。
而"训完看 mAP / 每类 AP / IoU / 置信度"恰恰是最需要**可复现**的一步 ——
论文和答辩里的数字必须能随时重跑出来，而不是只存在于某次训练的日志里。

更麻烦的是"IoU"这个词在本平台里有**三种**互不相同的用途：

| 用途 | 出处 | 取值 |
|---|---|---|
| NMS 去重阈值 | `--iou`（`EvalSettings.iou`） | `0.7` |
| mAP 的 TP 判定门限 | 由 mAP 口径本身决定，**无 CLI 开关** | `0.5`（mAP50）/ `0.5:0.05:0.95` 共 10 档（mAP50-95） |
| 匹配口径的匹配门限 | `evaluation/iou.py` 的 `IOU_MATCH_THRESHOLD` | `0.5` |

而 mAP50 / mAP75 / mAP50-95 虽然"沿 IoU 轴看"，回答的却是**"能不能把目标找到"**，
回答不了**"框贴得有多紧"**：框的位置偏半个身位时 mAP50 可能仍然很高（0.5 门限很宽松），
但下游的测距 / 跟踪 / 裁剪都会受影响。

### 备选方案

- ① 只保留训练日志里的指标，不做独立评估；
- ② 做独立评估，但只报官方口径（mAP 三件套 + 每类 AP/P/R）；
- ③ 独立评估，**官方口径与匹配口径并列**，并在报告、渲染、文档三处写明"不可混用"（**采纳**）。

### 决定

**1. 评估独立成子系统**：自己的入口（`odp-eval`）、自己的配置
（`apps/platform/configs/runtime/eval.yaml`）、自己的报告
（`runs/detect_eval/<run_id>/`）。`evaluation/` 下四个模块各司其职：

| 模块 | 职责 |
|---|---|
| `settings.py` | `EvalSettings` —— 全部可调项（默认值只声明一次） |
| `dataset.py` | 只读安全的数据集视图（硬链接） |
| `metrics.py` | 官方口径的指标整理（**纯函数，不 import ultralytics**，可离线单测） |
| `iou.py` | 匹配口径的 IoU 分析（纯函数部分同样可离线单测） |
| `report.py` | 报告纯数据 + 三种出口（logger / json / csv） |
| `service.py` | 端到端串联（模型可注入，测试可用鸭子类型替身离线跑完整条链路） |

**2. 两处默认值的取向不是随手填的。**

| 字段 | 默认 | 理由 |
|---|---|---|
| `device` | `cpu` | 本机显存只有 8GB，评估不该去抢训练的卡 |
| `conf` | `0.001` | **val 阶段必须用极低阈值**：用 0.25 之类的部署阈值去 val，会凭空砍掉 P-R 曲线的左半段，算出来的 mAP 会系统性偏低 |
| `conf_thresholds` | `(0.05 … 0.7)` | 与 `conf` 是**两件事**：后者为算 mAP，前者为"部署时选哪个阈值" |

**3. 平均口径：分母是"有真值的类"。**

`metrics.mean_ap()` 与框架的 `map50` 用**同一口径**，所以不排除任何类时
`stratified` 的第一块与 `overall.map50` 应当相等 —— 有一条测试专门守这个一致性。
没有真值的类**显式标成** `evaluated=false` + `note: "没有真值（—）, 未参与评测"`，
**不补 0**：补 0 会把"没评测"说成"评测得很差"。
报告渲染与 CSV 里 `None` 显示为破折号 / 空单元格，也是同一个理由。

额外提供 `--exclude-classes` / `--classes` 两套分层口径（**互斥**，同时给会 `ValueError`）——
因为一个框数少、又难的小类会把按类平均的 mAP 明显拖下来，两件事要分开说清。
拼错的类名不会静默失效：`_warn_unknown_classes` 会警告"数据集之外的类名（不会起作用）"。

**4. 置信度扫描是"逐阈值各跑一次 val"，不是从曲线推。**

框架给的 P-R 曲线横轴是**召回率**，不是置信度 —— 没有 "conf → R" 的对应关系，推不出来。
代价是 N 倍 val 时间，所以既可配置，也能用 `--no-conf-sweep` 关掉，
并且**把这个代价如实写在文档里**（而不是假装它免费）。

推荐阈值规则（`metrics.recommend_threshold`，`target_precision` 默认 `0.90`）：
在**精度 ≥ target_precision** 的阈值里取**召回率最大**者（而不是取最大 F1）；
并列时取精度更高者，再并列取阈值更低者；**若没有任何阈值达标，不硬推荐** ——
返回 `status: "目标精度不可达"`，给出 F1 最高的阈值作参考，并在 `reason` 里写明
"不构成「达标」结论"。

**5. 匹配式 IoU 分析（`evaluation/iou.py`）—— 另一套口径，并列但绝不混用。**

- 预测来自 `model.predict(conf=settings.conf, iou=settings.iou, …)`，
  阈值**取自配置**，不在模块里另写死一个数，这样"这次按什么阈值算的"永远能在报告的
  `settings` 与 `iou_analysis.conf` / `iou_analysis.nms_iou` 里查到；
- **只允许同类**预测与真值两两求 IoU；按 IoU **降序贪心一对一**匹配
  （排序键带下标，保证 IoU 并列时结果可复现 —— "同一份输入永远得到同一份匹配"）；
- 只有 `IoU >= IOU_MATCH_THRESHOLD`（0.5）才算匹配；没配上的预测算 FP，
  没配上的真值算 FN；
- 在匹配对上统计 IoU 的 `mean` / `median` / `min` / `max`，以及
  `0.50-0.60 … 0.90-1.00` **五档直方图**；直方图 `share` 的分母是**匹配对数**
  （它回答"配上的这些框里有多少落在这一档"）；
- 逐图明细在 `per_image`（每图的真值数 / 预测数 / 匹配数 / FP / FN / mean_iou），
  匹配对明细落成 `iou_pairs.csv`；
- **`note` 字段负责说清口径**：
  `"匹配口径: 同类预测/真值按 IoU 降序贪心一对一, 门限 IoU>=0.5; 与官方 mAP 口径不同, 两者不可混用或相加"`。

**6. 一个真实且必须写明的坑：`conf` 太低会让匹配口径的 P 失真。**

`eval.yaml` 的默认 `conf` 是 `0.001`（给 val 用）。用它跑匹配，NMS 后会吐出**几百个
低置信度框**，于是"未匹配的预测（FP）"暴涨，匹配口径的 P 会低到没有意义。
**IoU 分布本身不受影响**（配上的还是那几个高分框）。
所以当 `conf <= IOU_LOW_CONF_HINT`（`0.01`）时，`note` 会追加一段说明：
这次 conf 属 val 级极低阈值、未匹配的预测里绝大多数是低置信度框、
**匹配口径的 P 偏低不代表交付质量**、要看部署阈值的匹配口径请提高 `--conf`。
用 `--no-iou-analysis` 可整块跳过（省一遍 predict）。

### 理由

1. "可复现"是评估存在的**唯一理由**。训练日志会滚、格式会随框架变、想重看只能重训。
2. 把两套口径并列输出，是因为它们回答不同问题且**都有用**；
   但混着说（相加、相除、拿一个当另一个的解释）会得出错误结论 ——
   所以纪律必须写在代码注释、`note` 字段、报告渲染与文档**四处**，不能只靠口头约定。
3. 纯函数化的 `metrics.py` / `iou.py` 让判据可以完全离线单测：
   不需要权重、不需要 GPU、不需要网络。阈值推荐、均值口径、警告触发、贪心匹配
   都能被测得很细。

### 后果

- **正面**：答辩里的数字可以随时重跑；每类指标、两套口径、IoU 分布、扫描表都在
  结构化报告里；`warnings` 把"这个数为什么小"和数字一起给出。
- **负面**
  - 置信度扫描与 IoU 分析各要额外跑一遍（可关）；
  - 匹配口径的 P/R 在默认 `conf` 下**不能直接引用** —— 这是使用者的负担，
    只能靠 `note` 与文档把话说清楚；
  - 报告 JSON 体积不小（含降采样的 P-R 曲线点集，`pr_curve_points` 默认 200）。
- **中性**：`EvalSettings` 只认 `evaluation` 一节，未知键会经
  `report_unknown_keys` 报出来（不静默忽略）。

### 撤销条件

- 若框架将来给出 `conf → R` 的对应关系，置信度扫描可以改为从曲线推导，
  省掉 N 倍 val 时间；
- 若决定只保留一套口径，则删除 `iou.py` 与 `iou_analysis` 字段，并在本 ADR 标注 `Superseded`。

## 决策三（缺陷修正）：标签目录推导从"只认 Roboflow 布局"改为多候选探测

### 背景 —— 原来的推导为什么会在本仓库自己的布局下失效

`evaluation/dataset.py` 的 `build_dataset_view()` 在解析出 split 的图像目录之后，
要推导**配套的标签目录**，因为"数真值框"（`count_instances`）和"把标签复制进视图"
都要用它。

**原先的实现只认一种布局**：Roboflow 式的嵌套布局 ——
`valid/images/` 与 `valid/labels/` 是**同级兄弟**，即
`images_dir.parent / "labels"`。

而本仓库 D3 流水线物化出来的 split 布局是：

```
data/processed/<name>/images/val/    ← yaml 里的 val 指向这里
data/processed/<name>/labels/val/    ← 标签在 images 的【祖父】目录下的 labels/<split>
```

此时 `images_dir.parent / "labels"` = `.../images/labels` —— **这个目录不存在**。
后果是静默的、而且是双重的：

1. `count_instances()` 在一个不存在的目录里 `glob("*.txt")` → 得到 `(0, 0, …)`，
   于是报告里每类的 `instances` 恒为 **0**，`instances_per_class` 全零；
2. 视图的 `labels/` 里一个标签都没被复制进去 → 交给框架的视图里**图没有配套标签**，
   于是框架给出的 `ap_class_index` 为空 → **所有类都被标成"无真值"**。

两者叠加的效果是：**指标全废，但流程不报错**。这正属于"静默失败"那一类，
比直接崩掉难查得多。

### 备选方案

- ① 让 `odp-transform` 改成输出 Roboflow 式布局 —— 改动会波及物化、
  yaml 的 `train/val/test` 值、质检快照与 slice 统计，牵动面太大；
- ② 让使用者自己在 yaml 里显式写 `labels` 路径 —— 把仓库自身的布局问题
  转嫁给使用者，且破坏"yaml 只用 `path` + `images/<split>`"的约定；
- ③ 在**读取端**把已知布局都试一遍（**采纳**）。

### 决定

`resolve_labels_dir(images_dir)` 按顺序探测**三个候选**，返回 `(目录 或 None, 说明)`：

| 顺序 | 候选 | 对应布局 |
|---|---|---|
| ① | `images_dir.parent / "labels"` | Roboflow 嵌套布局（`valid/images/` + `valid/labels/`） |
| ② | `images_dir.parent.parent / "labels" / images_dir.name` | **本仓库 D3 流水线布局**（`images/val/` + `labels/val/`） |
| ③ | `images_dir.parent.parent.parent / "labels" / images_dir.name` | 更上一层目录（多包一层的数据集布局） |

选择规则：

1. 在**已存在**的候选里，取**第一个含 `*.txt` 的**；
2. 都空但目录存在 → 返回第一个存在者，并记 `标签目录 ... 存在但里面没有 .txt` 的说明；
3. 全都不存在 → 返回 `None`，说明里**列出全部候选路径**。

配套的三条纪律：

- **说明无论成败都会返回**（`notes`）—— 排查"为什么真值框是 0"时它就是第一份证据；
  `build_dataset_view()` 把它并进 `DatasetView.resolution_notes`，报告里可见。
- 兜底：`labels_dir` 为 `None` 时仍取 `images_dir.parent / "labels"` 作为 `Path`
  （下游按目录用，不做 `None` 分支），避免在调用点散落判空。
- 坏标签文件**跳过而不抛**（`count_instances` 与 `iou.parse_label_file` 都如此）——
  一个坏标签不该让整场评估失败；抓坏标签是 D4 质检的职责。

同一个"多候选 + 留说明"的模式也用在 split 目录解析上
（`_candidate_forms` 剥前导 `../`、`candidate_bases` 依次尝试
`path` / yaml 目录 / yaml 父目录），见 [ADR-002](ADR-002-dataset-yaml-paths.md)。

### 理由

1. 读取端宽容，把"布局有几种"挡在子系统边界之外；下游面对的是解析好的真实目录。
2. 这是**本仓库自己的布局**导致的问题，修在读取端而不改输出布局，
   不会把机器人传出去。
3. 保留 `resolution_notes` 让"解析到哪了"成为报告的一部分 ——
   下次再有布局不认识，第一眼就能看到是哪几个候选都试过了。

### 后果

- **正面**：本仓库 D3 布局、Roboflow 导出、多包一层的第三方导出都能直接用；
  `instances` 不再恒为 0，也不再把"有真值的类"误标成"无真值"。
- **负面**：三个候选的顺序意味着"如果三个候选都存在且都有 txt"，会选中第一个 ——
  在畸形数据集上可能选到不是你想的那个。这种情况由 `resolution_notes` 记录下来，
  排查时可见。
- **中性**：不影响 D3 的产物布局与 yaml 契约，指纹与章都不受影响。

### 撤销条件

- 若统一了数据集物化布局（例如全部采用 `images/<split>` + `labels/<split>`），
  可把候选收敛为一条，并在本 ADR 说明；
- 若支持在 yaml 里显式声明标签目录，则显式声明优先级最高，候选探测降为兜底。
